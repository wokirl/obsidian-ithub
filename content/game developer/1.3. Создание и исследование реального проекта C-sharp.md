## 1. Цель изучения

Научиться самостоятельно создавать, исследовать и понимать структуру реального проекта C-sharp на платформе .NET.

В рамках темы изучены:

- создание проекта через .NET CLI;
    
- назначение файлов и каталогов проекта;
    
- конфигурация проекта через `.csproj`;
    
- работа SDK и MSBuild;
    
- процесс сборки и запуска;
    
- восстановление зависимостей через NuGet;
    
- автоматическая генерация файлов;
    
- механизм `ImplicitUsings`;
    
- автоматическое включение исходных файлов в компиляцию.
    

## 2. Создание проекта

Для создания консольного проекта использовалась команда:

```
dotnet new console -n GameDevLab
```

Здесь:

- `dotnet` — интерфейс командной строки .NET CLI;
    
- `new` — создание нового проекта;
    
- `console` — шаблон консольного приложения;
    
- `-n` — параметр имени проекта;
    
- `GameDevLab` — название создаваемого проекта.
    

Установленная версия SDK:

```
9.0.315
```

Целевая платформа проекта:

```
net9.0
```

### Полученная структура

```
GameDevLab/
├── GameDevLab.csproj
├── Program.cs
├── bin/
└── obj/
```

## 3. Файл проекта .csproj

`.csproj` — XML-файл, содержащий настройки проекта, которые используются .NET SDK и MSBuild при сборке.

Исходное содержимое:

```
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net9.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

</Project>
```

### 3.1. OutputType

Определяет тип выходного результата проекта.

|Значение|Назначение|
|---|---|
|`Exe`|Исполняемое приложение|
|`Library`|Библиотека|

Если изменить `Exe` на `Library`, проект будет собираться как библиотека, а не как самостоятельное приложение.

### 3.2. TargetFramework

```
<TargetFramework>net9.0</TargetFramework>
```

Определяет целевую платформу .NET, для которой создаётся приложение.

Важно различать:

- .NET SDK — инструменты разработки и сборки;
    
- Target Framework — целевую платформу проекта;
    
- Runtime — среду выполнения приложения.
    

### 3.3. ImplicitUsings

```
<ImplicitUsings>enable</ImplicitUsings>
```

Управляет автоматической генерацией глобальных директив `using`.

При включённой настройке SDK генерирует файл:

```
GameDevLab.GlobalUsings.g.cs
```

Его содержимое в нашем проекте:

```
// <auto-generated/>
global using global::System;
global using global::System.Collections.Generic;
global using global::System.IO;
global using global::System.Linq;
global using global::System.Net.Http;
global using global::System.Threading;
global using global::System.Threading.Tasks;
```

Благодаря этому можно писать:

```
Console.WriteLine("Hello, World!");
```

Вместо:

```
System.Console.WriteLine("Hello, World!");
```

**Что означает global using?**

Обычный `using` действует в пределах файла или соответствующей области действия.

`global using` распространяется на все исходные файлы текущей компиляции.

`global::` указывает на глобальное пространство имён, от которого начинается разрешение имени.

#### Эксперимент с ImplicitUsings

Было изменено:

```
<ImplicitUsings>enable</ImplicitUsings>
```

На:

```
<ImplicitUsings>disable</ImplicitUsings>
```

После этого компиляция следующего кода завершилась ошибкой:

```
Console.WriteLine("Hello, World!");
```

Ошибка:

```
error CS0103: Имя "Console" не существует в текущем контексте.
```

Однако следующий вариант продолжил работать:

```
System.Console.WriteLine("Hello, World!");
```

Также можно вручную подключить пространство имён:

```
using System;

Console.WriteLine("Hello, World!");
```

**Вывод:** класс `Console` не исчезает при отключении `ImplicitUsings`. Просто компилятор больше не получает автоматическую глобальную директиву для пространства имён `System`.

### 3.4. Nullable

```
<Nullable>enable</Nullable>
```

Включает анализ nullable reference types.

Эта настройка помогает компилятору обнаруживать потенциальные ошибки, связанные с использованием ссылочных типов, которые могут содержать `null`.

Важно: она не превращает строки в nullable автоматически и не добавляет обязательные проверки во время выполнения.

## 4. Program.cs и точка входа

Исходное содержимое:

```
// See https://aka.ms/new-console-template for more information
Console.WriteLine("Hello, World!");
```

`Program.cs` — распространённое название файла с кодом программы, но само название файла не определяет точку входа.

### Top-level statements

В современном C-sharp можно писать инструкции непосредственно на верхнем уровне файла:

```
Console.WriteLine("Hello, World!");
```

Компилятор самостоятельно формирует необходимую структуру с точкой входа.

В традиционном варианте точкой входа является метод `Main`.

Упрощённое представление:

```
class Program
{
    static void Main(string[] args)
    {
        Console.WriteLine("Hello, World!");
    }
}
```

Это концептуальное представление, а не точная копия сгенерированного компилятором кода.

**Важно:** не следует путать имя файла `Program.cs` с методом `Main`. Это разные сущности.

## 5. Сборка и запуск проекта

Для сборки использовалась команда:

```
dotnet build
```

Для запуска:

```
dotnet run
```

Результат выполнения:

```
Hello, World!
```

### 5.1. Что происходит при сборке?

Упрощённая последовательность:

```
Исходные файлы (.cs)
        |
        v
.NET SDK и MSBuild
        |
        v
Подготовка проекта и зависимостей
        |
        v
Компилятор C-sharp
        |
        v
IL + метаданные
        |
        v
Сборка .NET
```

В результате появляются файлы сборки и сопутствующие данные.

### 5.2. Каталог bin

`bin` содержит результаты сборки.

В нашем проекте:

```
bin/
└── Debug/
    └── net9.0/
        ├── GameDevLab.dll
        ├── GameDevLab.exe
        ├── GameDevLab.runtimeconfig.json
        ├── GameDevLab.deps.json
        └── GameDevLab.pdb
```

Назначение файлов:

|Файл|Назначение|
|---|---|
|`GameDevLab.dll`|Основная управляемая сборка с IL и метаданными|
|`GameDevLab.exe`|Windows apphost — нативный запускатель приложения|
|`GameDevLab.runtimeconfig.json`|Настройки среды выполнения|
|`GameDevLab.deps.json`|Информация о зависимостях|
|`GameDevLab.pdb`|Отладочная информация|

**Важное различие:** `GameDevLab.exe` не содержит всю основную логику приложения. В нашем случае она находится в `GameDevLab.dll`.

### 5.3. Debug и Release

Результаты сборки располагаются в каталоге конфигурации:

```
bin/
├── Debug/
└── Release/
```

- `Debug` — конфигурация для разработки и отладки.
    
- `Release` — конфигурация для выпуска, обычно с оптимизациями.
    

### 5.4. Каталог obj

`obj` содержит промежуточные результаты сборки и данные, необходимые инструментам .NET.

Примеры:

```
obj/
├── Debug/
│   └── net9.0/
├── GameDevLab.csproj.nuget.dgspec.json
├── GameDevLab.csproj.nuget.g.props
├── GameDevLab.csproj.nuget.g.targets
├── project.assets.json
└── project.nuget.cache
```

Внутри могут находиться:

- сгенерированные исходные файлы;
    
- промежуточные результаты компиляции;
    
- сведения о зависимостях;
    
- настройки и данные MSBuild;
    
- кэшированные результаты операций.
    

## 6. NuGet и восстановление зависимостей

NuGet — система управления пакетами .NET.

Она позволяет получать сторонние библиотеки и управлять зависимостями проекта.

Основные задачи:

1. Получение необходимых пакетов.
    
2. Определение зависимостей пакетов.
    
3. Разрешение совместимых версий.
    
4. Восстановление необходимых компонентов.
    
5. Подготовка данных для сборки.
    

### Транзитивные зависимости

Допустим:

```
Наш проект
    |
    v
Пакет A
    |
    v
Пакет B
    |
    v
Пакет C
```

Если проект использует пакет A, ему могут понадобиться B и C, даже если мы самостоятельно их не подключали.

Такие зависимости называются транзитивными.

Восстановление зависимостей является частью стандартного процесса сборки .NET. Поэтому оно выполняется и в проектах без пользовательских сторонних библиотек.

## 7. Автоматически генерируемые файлы

В ходе исследования были найдены три важных файла.

### 7.1. GameDevLab.GlobalUsings.g.cs

Содержит автоматически сгенерированные глобальные директивы `using`.

Назначение — обеспечить доступ к стандартным пространствам имён без необходимости вручную подключать их в каждом исходном файле.

### 7.2. GameDevLab.AssemblyInfo.cs

Содержит атрибуты сборки.

Пример:

```
[assembly: System.Reflection.AssemblyCompanyAttribute("GameDevLab")]
[assembly: System.Reflection.AssemblyConfigurationAttribute("Debug")]
[assembly: System.Reflection.AssemblyVersionAttribute("1.0.0.0")]
```

Атрибуты — специальные конструкции, добавляющие метаданные к программным элементам.

В данном случае `assembly:` указывает, что атрибут относится ко всей сборке.

Основные атрибуты:

|Атрибут|Назначение|
|---|---|
|`AssemblyCompany`|Компания|
|`AssemblyConfiguration`|Конфигурация сборки|
|`AssemblyFileVersion`|Версия файла|
|`AssemblyInformationalVersion`|Информационная версия|
|`AssemblyProduct`|Название продукта|
|`AssemblyTitle`|Название сборки|
|`AssemblyVersion`|Версия сборки|

Эти атрибуты не содержат игровую логику. Они описывают сборку.

Для постоянного изменения метаданных следует использовать настройки проекта, а не редактировать генерируемый файл вручную.

### 7.3. GameDevLab.GeneratedMSBuildEditorConfig.editorconfig

Это генерируемый конфигурационный файл для инструментов разработки и анализаторов кода.

Пример:

```
is_global = true
build_property.TargetFramework = net9.0
build_property.RootNamespace = GameDevLab
build_property.ProjectDir = D:\...\GameDevLab\
build_property.EffectiveAnalysisLevelStyle = 9.0
```

Некоторые параметры:

|Параметр|Назначение|
|---|---|
|`is_global`|Указывает на глобальную область действия конфигурации|
|`TargetFramework`|Целевая платформа|
|`RootNamespace`|Корневое пространство имён|
|`ProjectDir`|Путь к проекту|
|`EffectiveAnalysisLevelStyle`|Уровень правил анализа стиля|

Этот файл не является исходным кодом программы. Он предоставляет настройки инструментам разработки.

## 8. Автоматическое включение исходных файлов

В стандартном SDK-проекте C-sharp новые файлы `.cs` автоматически включаются в компиляцию.

Например:

```
GameDevLab/
├── GameDevLab.csproj
├── Program.cs
├── Player.cs
└── Enemy.cs
```

Не требуется вручную регистрировать `Player.cs` и `Enemy.cs` в `.csproj`.

.NET SDK использует механизм автоматического включения исходников в элементы `Compile`.

Упрощённая схема:

```
Создание Player.cs и Enemy.cs
             |
             v
SDK обнаруживает исходные файлы
             |
             v
Файлы включаются в Compile
             |
             v
Компилятор получает исходники
             |
             v
Создаётся сборка
```

Это не означает, что классы автоматически выполняют свою логику. Они становятся частью сборки и могут использоваться другими компонентами программы.

**Исключения:** автоматическое включение может быть изменено настройками проекта, например при отключении стандартных элементов компиляции или явном исключении файлов.

## 9. Очистка проекта перед передачей

В стандартном проекте каталоги `bin` и `obj` можно удалить.

```
GameDevLab/
├── GameDevLab.csproj
├── Program.cs
├── Player.cs
└── Enemy.cs
```

При следующей сборке необходимые каталоги и промежуточные файлы будут созданы заново.

Однако важно хранить все исходные файлы, конфигурации и необходимые ресурсы проекта.

Сгенерированные файлы не должны быть единственным местом хранения важных пользовательских настроек.

## 11. Принципы, вызвавшие больше всего вопросов

### 11.1. Имя файла не определяет его назначение

`Program.cs` не обязательно содержит точку входа.

Точку входа определяет структура программы и правила компилятора.

### 11.2. Пространство имён и класс — не одно и то же

`System` — пространство имён.

`Console` — класс внутри этого пространства имён.

`Console.WriteLine()` — вызов метода класса `Console`.

Поэтому при отсутствии подключения `System` можно использовать полное имя:

```
System.Console.WriteLine("Hello");
```

### 11.3. Генерируемый файл и исходный файл — разные вещи

`GameDevLab.GlobalUsings.g.cs` генерируется SDK.

Он участвует в компиляции, но не является файлом, который разработчик должен постоянно редактировать вручную.

### 11.4. Сборка и логика выполнения — разные понятия

Изменение метаданных сборки, например `AssemblyTitle`, само по себе не меняет алгоритмы программы.

### 11.5. Наличие класса не означает его выполнение

Добавление `Player.cs` включает класс в сборку, но не создаёт игрового персонажа автоматически.

Для этого программа должна явно использовать соответствующий класс.
